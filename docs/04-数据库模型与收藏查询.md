# 数据库模型与收藏查询

## 1. 数据职责

Neon Postgres 是线上业务数据的唯一事实来源，Prisma Schema 位于 `prisma/postgres/schema.prisma`。在线 API 使用 `POSTGRES_PRISMA_URL` 的池化连接；迁移脚本使用 `DATABASE_URL_UNPOOLED`。

主要模型分为四组：

- 内容：`VocabularyCategory`、`VocabularyWord`、`VocabularyExample`。
- 发音和媒体：`VocabularyPronunciation`、关联表、音频和生成任务。
- 用户：`User`、`AuthToken`。
- 收藏与运维：`Collection`、`Favorite`、`ErrorLog`。

## 2. 收藏词条标识

前端使用 `wordKey` 表示词条：

- 存在 `wordEntryId` 时直接使用其字符串值。
- 否则使用 `translation:<translationId>`。

词条查询必须同时使用 `recordId` 和 `wordKey`。不能假设同一个 `wordKey` 在所有分类中都唯一；Favorite 的数据库唯一约束因此是 `(collectionId, recordId, wordKey)`。服务端和前端都使用 JSON 序列化的二元组作为内存键，避免简单字符串拼接产生分隔符冲突。

## 3. 收藏列表批量加载

`GET /api/collections` 的链路为：

1. 按 `userId` 一次读取用户的收藏夹和 Favorite 关系。
2. `findWords()` 对 `(recordId, wordKey)` 去重。
3. Prisma 每 250 个复合条件执行一次 `VocabularyWord.findMany`，顺序批量读取词条、分类和例句。
4. 服务层返回复合键 Map，路由按原收藏顺序组装响应。

这样把原来的“1 次收藏查询 + N 次词条查询”收敛为有上限的少量批查询，并避免同一词卡跨收藏夹重复读取。路由层不得重新引入逐条 Prisma 查询。

新增、判断星标和删除收藏必须使用相同复合身份。只按 `wordKey` 删除或标记，会影响其他分类下具有相同词典词条 ID、但词义不同的卡片。

唯一约束迁移位于公开与私有仓库的 `prisma/postgres/migrations/005_favorite_identity.sql`。私有仓库负责数据库维护，应使用 `DATABASE_URL_UNPOOLED` 在部署依赖新约束的 Prisma Client 之前执行；构建过程不会自动运行迁移。

当前接口仍一次返回用户全部收藏内容。若真实用户收藏量增长，应优先测量响应体、数据库时间和前端渲染，再考虑按收藏夹延迟加载或分页；不要只把 N+1 改成一个无限大的响应。

## 4. 查询和索引原则

- 新索引应由真实查询计划验证，不能看到过滤字段就直接添加。
- `%keyword%` 模糊搜索通常不能充分使用普通 B-tree；应在代表性数据上比较 trigram、全文搜索或前缀策略。
- Neon 上分析安全的只读查询时，可使用 `EXPLAIN (ANALYZE, BUFFERS, PREFETCH, FILECACHE)` 观察 Postgres buffer 和 Neon 本地文件缓存，但 `ANALYZE` 会实际执行语句。
- 修改 Schema 时必须提交对应 SQL 迁移，并在隔离的数据库分支或测试环境验证后再应用生产。

## 5. 数据安全

收藏、用户和管理员接口必须始终在服务端按当前用户或管理员角色过滤。浏览器传来的 ID 只是输入，不代表所有权。密码哈希、令牌摘要和连接信息不得通过数据库浏览接口返回。
